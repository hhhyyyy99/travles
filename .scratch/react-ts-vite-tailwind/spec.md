# 将旅行手册迁移至 React + TypeScript + Vite + Tailwind CSS

Status: ready-for-agent

## Problem Statement

当前呼伦贝尔旅行手册使用原生 HTML、CSS 和 JavaScript，多份脚本依靠加载顺序、全局对象与直接 DOM 操作协作。行程、住宿基地、地图路线和打印内容之间存在状态联动，继续维护这些功能需要处理分散的渲染和生命周期。

用户希望将项目改造成 React + TypeScript + Vite + Tailwind CSS 项目，获得组件化开发、类型检查、开发热更新和可部署的生产构建，同时保留已经完成的旅行规划功能。

## Solution

将现有旅行手册完整迁移到指定技术栈。React 管理页面与交互状态，TypeScript 描述业务数据和外部服务边界，Vite 提供开发和生产构建，Tailwind CSS 承担应用界面样式。迁移后继续提供相同的行程、住宿管理、地图、出发清单和打印体验，同源访问时能够读取既有浏览器数据，并兼容既有住宿备份。

## User Stories

1. As an 开发者, I want 使用 React 组件维护旅行手册, so that 页面职责和交互边界更清晰。
2. As an 开发者, I want 使用 TypeScript 编写应用逻辑, so that 数据形状和调用错误能在开发阶段发现。
3. As an 开发者, I want 使用 Vite 启动开发服务并热更新, so that 修改界面后能快速看到结果。
4. As an 开发者, I want 使用 Tailwind CSS 编写界面样式, so that 布局和响应式规则采用一致方式维护。
5. As an 开发者, I want 运行独立类型检查, so that 构建转译成功不会掩盖类型错误。
6. As an 开发者, I want 构建并预览静态生产产物, so that 可以验证实际部署版本。
7. As an 开发者, I want 获得依赖锁定和启动说明, so that 新环境能复现项目。
8. As an 用户, I want 原有旅行手册入口仍可访问, so that 已保存的链接继续有效。
9. As an 用户, I want 保留七天六晚的行程内容与景点顺序, so that 技术迁移不会改变旅行计划。
10. As an 用户, I want 切换每日行程并查看对应地图和详情, so that 可以逐日了解安排。
11. As an 用户, I want 查看全程地图与住宿摘要, so that 能掌握整段旅行。
12. As an 用户, I want 在手机和桌面保持现有视觉层次与可用布局, so that 可以在不同设备查看行程。
13. As an 用户, I want 勾选出发清单并在刷新后保留, so that 不必重新记录准备进度。
14. As an 用户, I want 迁移后继续读取原有住宿基地和晚次选择, so that 已规划的数据不会丢失。
15. As an 用户, I want 搜索酒店或住宿区域并确认位置, so that 能将实际住宿加入行程。
16. As an 用户, I want 搜索不可用时仍能通过地图选点, so that 可以继续录入住宿。
17. As an 用户, I want 获得重复住宿提醒并自主选择复用或继续创建, so that 能避免误操作。
18. As an 用户, I want 将住宿保存为备选或应用于一晚及多晚, so that 能逐步安排住宿。
19. As an 用户, I want 编辑共用住宿后关联晚次同步更新, so that 住宿信息保持一致。
20. As an 用户, I want 删除备选住宿并在删除使用中住宿时获得保护, so that 行程引用不会失效。
21. As an 用户, I want 恢复单晚默认住宿并保留默认基地, so that 能撤销安排调整。
22. As an 用户, I want 更换住宿后更新当天终点和次日出发点, so that 路线符合当前安排。
23. As an 用户, I want 路线重算时看到更新中、成功或未更新的反馈, so that 不会将过期估算误认为新结果。
24. As an 用户, I want 快速切换住宿时只显示最新有效路线结果, so that 延迟响应不会覆盖新选择。
25. As an 用户, I want 高德使用已有配置自动加载且失败后可以重试, so that 无需手动填写凭据。
26. As an 用户, I want 地图服务不可用时仍可查看行程和参考路线, so that 网络异常不会让手册失去作用。
27. As an 用户, I want 导出住宿备份并预览、取消或确认整体恢复, so that 可以手动保存和迁移安排。
28. As an 用户, I want 旧版有效备份仍能导入, so that 技术升级不影响已有备份。
29. As an 用户, I want 无效备份或存储写入失败时保留原有数据并看到提示, so that 不会误以为保存成功。
30. As an 同行者, I want 打印或另存为 PDF 时包含当前住宿地址与备注, so that 离线查看的行程完整。
31. As an 键盘用户, I want 继续通过键盘操作表单、弹窗和地图位置确认, so that 核心规划流程可访问。
32. As an 开发者, I want 既有行为测试在迁移后继续提供保障, so that 架构调整不会悄悄减少功能。

## Implementation Decisions

- 采用 React、TypeScript、Vite 和 Tailwind CSS；实施时选择彼此兼容的稳定版本、声明所需 Node 版本并提交依赖锁文件，不在规格中猜测最新版本号。
- 这是技术栈迁移，保留现有文案、行程数据、景点顺序、视觉风格、响应式布局和业务规则。不以重新设计页面作为迁移前置条件。
- 将行程布局、每日选择与详情、地图容器、住宿编辑与管理、备份恢复、出发清单和打印视图按职责组件化。页面内容与表单状态由 React 驱动，不能仅用 React 外壳加载全部旧业务脚本作为最终交付。
- 将应用业务源码迁移为 TypeScript/TSX 和显式模块依赖，启用严格类型检查。既有 CommonJS 测试或开发工具可按需要保留；第三方 SDK 和预置大型资源不要求逐行改写。
- 统一建模住宿基地、每晚住宿选择、行程日、路线估算与请求状态。明确经纬度顺序和 WGS-84/GCJ-02 转换边界，保留已有坐标转换语义。
- 住宿安排保留单一权威状态，由此派生每日住宿、使用中基地数量、路线端点、摘要和打印内容。优先采用 React 状态与上下文及明确的业务模块，不预设额外全局状态库。
- 将 Leaflet 与高德集成封装为有类型的适配边界。第三方地图可管理自身容器内部 DOM，应用界面不再依赖全局业务对象相互调用；SDK 必需的全局入口可保留。
- 地图实例、订阅、计时器和异步请求具有明确的创建与清理过程；开发模式重复挂载和热更新不能产生重复地图、监听器或查询。使用失效标识等机制拒绝过期响应。
- 保留预置路线、地图降级、搜索确认、重复提示、默认配置自动加载与重试，以及住宿变化后的相关路段重算。失败不撤销已保存住宿，也不展示旧距离为新住宿的有效估算。
- 保持现有本地存储键名、版本和有效数据格式兼容，住宿数据与清单独立保存。存储异常保留当前有效状态，并给出准确提示。开发端口或部署域名变化会改变浏览器存储源，使用原访问源验证兼容，跨源迁移使用住宿备份。
- 保留现有备份格式与整份恢复语义，运行时验证导入数据、版本、坐标及引用完整性；TypeScript 类型不能替代外部输入校验。
- Tailwind 实际承担应用布局、间距、颜色、排版和响应式样式。允许保留第三方地图样式、必要的全局规则和打印分页规则；不能只安装 Tailwind 而继续将全部应用样式留在旧样式系统。
- 保留当前本地高德配置的接入能力并提供无真实值的配置示例。实施时明确开发及生产配置方式；真实配置不写进规格、版本控制或测试夹具，浏览器所需配置不宣称为服务器秘密。
- 根入口与现有旅行页面入口继续进入同一应用，不维护两套页面实现。静态地图资源、图标和路线数据必须在生产构建后正确加载。
- 提供开发、启动兼容入口、类型检查、构建、预览和测试命令，说明端口与配置用法。生产产物能部署到静态托管，不依赖原有源码目录文件服务器。
- 保留既有测试场景，调整浏览器测试服务以加载真实 Vite 应用及生产产物。依赖旧全局业务对象的测试应改用页面操作、可见结果或持久化契约，不能为了测试保留无必要的生产全局桥接。

## Testing Decisions

- 主要测试边界为浏览器端完整用户流程，优先复用现有 Node test runner、Playwright 和可控高德 provider fixture。好测试验证可见行为、数据持久化和外部地图请求契约，不绑定组件层级、Hook 数量、内部状态或 CSS 类名。
- 覆盖行程、住宿、路线、清单、备份和打印的协同流程：选择日期 → 创建或搜索基地 → 应用多晚 → 检查地图和摘要 → 刷新 → 编辑与恢复默认 → 备份恢复 → 打印。
- 复用现有住宿核心、搜索、管理、备份、路线、默认地图加载和打印浏览器测试的场景。现有部分测试直接操作全局业务对象，因此需要迁移测试驱动方式，不能将原文件不变作为验收目标，也不能删掉异常场景换取通过。
- 保留现有路线工具及搜索纯逻辑测试，按模块迁移调整加载方式；继续验证缺失交通或时长数据不编造结果、坐标归一化及重复候选判断。不默认新增 React 组件测试层。
- 使用真实旧格式存储及备份样本验证升级兼容；验证存储失败、无效导入、悬空引用、取消恢复都不会破坏原数据。
- 使用确定性的外部服务响应覆盖自动加载、重试、搜索失败、路线失败、延迟和乱序。夹具只替代外部地图服务，不实现应用住宿逻辑；自动化验收不要求真实高德凭据。
- 在 Vite 开发服务下运行完整行为回归，并在生产构建预览下验证两个入口、资源加载及至少一条住宿保存后刷新恢复的主流程。类型检查和生产构建均须成功，不以 Vite 转译通过代替类型检查。
- 在桌面及手机视口核对主要页面、住宿弹窗与地图，验证键盘选点和焦点行为；检查打印模式的住宿信息、长文本与分页。
- 记录实际执行命令、结果与无法验证的外部依赖；不得将历史规格中的通过数量当作本次测试证据。

## Out of Scope

- 全新视觉设计、重写旅行内容、增加目的地、改变天数或自动重排行程。
- 账号、后端、数据库、云同步、在线共享、协作、预订和支付。
- Next.js、SSR 或为现有单页功能引入不必要的路由和状态框架。
- 重写地图 SDK、自建地图服务、独立 PDF 服务。
- 承诺浏览器数据跨域自动搬迁、清空旧存储或强制改用不兼容备份格式。
- 本次规格阶段直接执行应用迁移、提交代码、发布部署或修改已有已完成票。
