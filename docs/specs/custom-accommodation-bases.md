# 支持用户自定义添加住宿基地

状态：需求已逐项确认；测试边界待确认；尚未发布 issue。

## Problem Statement

现有行程的住宿基地、每晚住宿文案及路线端点固定。用户无法将自己选择的酒店、民宿或住宿区域用于行程，也无法让住宿变化同步反映在地图、驾车距离、次日出发点和打印行程中。

## Solution

允许用户创建私人住宿基地，通过每日住宿入口选择用于哪几晚，或保存为备选。保留既定行程天数与景点顺序，住宿变化只更新相关路线端点及驾车估算。数据保存在当前浏览器，提供备份恢复和包含住宿信息的打印行程。

## User Stories

1. As an 行程规划者, I want 添加具体酒店或民宿, so that 行程使用我实际选择的住宿。
2. As an 尚未预订住宿的用户, I want 添加住宿区域, so that 我可以先安排路线再决定酒店。
3. As an 用户, I want 填写基地名称并确认地图位置, so that 住宿能够被识别并参与路线计算。
4. As an 用户, I want 搜索地点后确认位置, so that 我能快速找到住宿。
5. As an 用户, I want 直接在地图上选点, so that 搜索不可用或找不到地点时仍能添加住宿。
6. As an 用户, I want 选填地址和备注, so that 我能保留入住所需的信息。
7. As an 用户, I want 收到疑似重复地点提醒但仍可继续添加, so that 我既能避免重复又能区分同址住宿。
8. As an 用户, I want 先将基地保存为备选, so that 我不必立即修改行程。
9. As an 用户, I want 从每日住宿旁更换基地, so that 我能直接调整某一晚的住宿。
10. As an 用户, I want 更换住宿时选择已有基地或新增基地, so that 我无需中断当前安排。
11. As an 用户, I want 将同一基地用于多晚, so that 连住安排无需重复创建地点。
12. As an 用户, I want 每晚可以恢复原有默认住宿, so that 我能撤销住宿方案的调整。
13. As an 用户, I want 集中查看和管理基地, so that 我能维护正在使用和备选的住宿。
14. As an 用户, I want 编辑基地后所有关联晚次同步更新, so that 行程不会出现相互矛盾的住宿信息。
15. As an 用户, I want 删除未使用的自定义基地, so that 我能清理备选列表。
16. As an 用户, I want 删除使用中的基地前先替换住宿, so that 行程不会留下缺失的住宿引用。
17. As an 用户, I want 保留不可删除的默认地点, so that 原始住宿方案始终可用。
18. As an 用户, I want 更换住宿后更新当天终点和次日出发点, so that 路线符合真实住宿安排。
19. As an 用户, I want 保持行程天数和景点顺序, so that 更换住宿不会意外重排旅行计划。
20. As an 用户, I want 重算相关驾车距离和时间, so that 我能评估住宿变化的影响。
21. As an 用户, I want 路线查询失败时仍可保存住宿并看到未更新提示, so that 网络问题不会丢失安排或误导判断。
22. As an 用户, I want 住宿区域按代表位置估算并说明这一点, so that 我知道距离并非具体酒店的精确结果。
23. As an 用户, I want 地图、每日住宿和住宿摘要保持一致, so that 我在不同视图中看到同一个方案。
24. As an 用户, I want 基地数量只统计行程实际使用的不同地点, so that 备选基地不会夸大住宿数量。
25. As an 用户, I want 刷新后保留基地和住宿选择, so that 我能继续之前的规划。
26. As an 用户, I want 了解数据仅存于当前浏览器, so that 我知道不会自动跨设备同步且清除数据会丢失设置。
27. As an 用户, I want 导出自定义基地及每晚选择, so that 我能备份或手动迁移安排。
28. As an 用户, I want 导入前校验并预览备份内容, so that 我能确认恢复的数据正确。
29. As an 用户, I want 明确确认后才整份替换当前设置, so that 导入不会意外覆盖安排。
30. As an 用户, I want 无效备份导入失败时保留当前数据, so that 错误文件不会破坏行程。
31. As an 同行者, I want 在打印或另存为 PDF 的行程中看到住宿名称、地址和备注, so that 我能查看入住安排。
32. As an 用户, I want 自定义基地不进入公共列表, so that 我的私人住宿安排不会自动公开。

## Implementation Decisions

- 保持现有静态网页架构，不引入账号、后端或数据库。当前代码的住宿以固定文案表达，路线拓扑和几何也是预置数据；现有地图起终点覆盖仅存在于内存，不能直接作为持久化住宿功能。
- 将住宿基地与每晚住宿选择分别建模。基地保存稳定标识、名称、位置、酒店或区域类型、可选地址及备注；每晚引用基地。同一基地可被多个晚次复用，未被引用的基地为备选。
- 保留默认住宿及恢复路径。默认地点不可删除；自定义地点支持编辑和删除，使用中的地点必须先完成替换才能删除。
- 名称和有效地图位置必填，不保存无法定位的住宿草稿。不要求预订证明，也不收集价格、电话等额外结构化字段。
- 新增地点支持高德搜索与地图选点。搜索失败不阻止手动选点，路线查询失败不撤销已保存的住宿。
- 名称相同且位置接近时提示疑似重复，提供使用已有基地的路径，也允许继续添加。接近距离的阈值属于实现参数，不构成强制合并规则。
- 提供每日“更换住宿”入口和集中住宿基地管理入口。基地数量按行程实际引用的不同基地统计，备选不计入。
- 由同一份有效住宿安排驱动每日文案、地图、住宿摘要、导航端点和打印内容，避免不同页面维护相互独立的住宿副本。
- 不更改行程天数、景点及游览顺序。替换住宿更新当天住宿终点和下一行程日出发点；编辑共用基地更新所有受影响路段。无下一行程日时不新增行程。
- 重新查询受影响路段的驾车路线、距离和时间，不能仅移动地图标记或更改导航链接。静态旧路线估算不得作为新住宿的有效结果展示。
- 路线状态应明确区分更新中、成功和未更新。失败时提示“路线未更新”，区域型基地说明按代表位置估算。异步返回不得用旧请求覆盖较新的住宿选择。
- 使用浏览器本地存储持久化自定义基地和晚次选择，与现有清单存储相互独立。明确告知本地保存、无自动同步及清除数据的影响；写入失败不能报告保存成功。
- 备份采用可校验且带格式版本的数据文件，包含自定义基地及每晚住宿选择。导入采用整份恢复，不做自动合并；校验字段、位置、版本及引用完整性，展示预览和替换提示，用户确认后整体生效。校验失败不修改现有数据。
- 通过浏览器打印及另存为 PDF 展示住宿名称、地址和备注。不创建公共基地目录或在线共享链接。

## Testing Decisions

以下为建议测试方案，尚待用户确认。

- 优先通过一个最高层的浏览器用户流程边界验证功能：添加基地 → 分配晚次 → 查看路线状态 → 刷新保留 → 导出恢复 → 打印。覆盖住宿管理、行程关联、持久化和路线呈现的协同行为，避免给每个内部函数建立独立测试边界。
- 地点搜索和路线服务使用可控响应覆盖成功、失败、缺少配置以及返回顺序颠倒，测试不依赖真实高德服务可用性。浏览器侧按真实交互与可见输出断言，不检查内部变量、私有调用次数或 DOM 的非语义结构。
- 验证必填信息、区域与酒店、搜索及选点、重复提示允许继续、备选不计数、同基地多晚使用、恢复默认、编辑联动和使用中删除保护。
- 验证只改变相关路线端点并保留景点顺序，次日出发点同步，失败不丢住宿且不展示旧估算为新结果，较旧响应不覆盖新选择。
- 验证刷新恢复、存储失败提示、备份往返、导入取消、无效或悬空引用备份拒绝且原数据不变、整份替换而非合并。
- 验证打印视图住宿信息完整、统计与行程一致，以及主要操作在移动屏幕和键盘操作下可完成。
- 现有先例是 Node 内置测试工具下的路线工具行为测试，覆盖交通数据缺失和时间缺失时不编造结果；目前未发现浏览器流程测试框架。保留并运行现有测试，新增最小浏览器验收能力。仅在确有独立行为且浏览器无法可靠覆盖时补充底层测试，不机械镜像实现。

## Out of Scope

- 账号、服务器存储、自动跨设备同步、公共基地列表、可编辑的在线共享或实时协作。
- 增加行程天数、自动调整景点顺序或重新规划整条旅行方案。
- 住宿预订、支付、实时房价、可订状态或预订状态管理。
- 缺少地图位置的文本住宿草稿，以及将区域代表位置当作具体酒店的精确定位。
- 默认基地删除、备份自动合并、独立 PDF 生成服务。
